Show developers how to ask
better PowerBuilder questions

Yes — you should absolutely have a prompt examples page. It turns the product from “cool demo” into “immediately usable workflow”. For enterprise teams this also reduces support load because people copy proven prompts instead of guessing.

1) Workspace discovery

Best first question after installation.

Inspect this PowerBuilder workspace and summarize:
1. which libraries exist,
2. the main application/window objects,
3. the biggest functional areas,
4. any obvious high-risk legacy hotspots.
Use MCP tools first, then give me a concise executive summary.

2) DataWindow audit

Great for DB-heavy teams.

Find all DataWindows related to customer and order workflows.
For each one:
- export the object,
- parse the SQL,
- list tables and columns,
- identify retrieval arguments,
- flag duplicate query patterns.
Then suggest consolidation opportunities.

3) Dependency tracing before refactor

High-value modernization prompt.

I want to refactor the customer lookup flow.
Find all objects that reference customer lookup logic, customer_id, or related helper functions.
Export the relevant source and build a dependency map.
Group the findings into low-risk, medium-risk, and high-risk change zones.

4) Explain a legacy module

Perfect for onboarding new developers.

Act like a senior PowerBuilder maintainer.
Inspect the sales module and explain:
- its main windows,
- important DataWindows,
- shared functions/user objects,
- likely transaction boundaries,
- where a new developer should start reading first.
Keep the explanation practical.

5) Safe edit plan

Use before writing back.

Before changing any objects, inspect the relevant libraries and exported sources.
Propose a step-by-step edit plan with:
- target objects,
- dependency impact,
- rollback points,
- verification steps,
- which edits should stay manual vs AI-assisted.
Do not modify anything yet.

6) Migration preparation

Strong enterprise/consulting angle.

Analyze this PowerBuilder workspace for modernization readiness.
Identify:
- heavily reused business rules,
- tightly coupled UI logic,
- DataWindows with complex SQL,
- candidates for service extraction,
- likely blockers for a .NET migration.
Then produce a phased migration brief.
